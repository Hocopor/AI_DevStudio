# AI DevStudio — Автономная AI-студия разработки
## Итоговое видение продукта v1.1 (финальное)

---

## 1. ОБЩАЯ КОНЦЕПЦИЯ

**AI DevStudio** — полностью автономная студия разработки программных продуктов, в которой роли сотрудников исполняют AI-агенты. Цель — самостоятельно находить рыночные возможности, разрабатывать и выводить на рынок цифровые продукты, генерируя реальную прибыль с минимальным участием владельца.

Владелец — **стратег и финальный арбитр**, а не операционный менеджер. Система сама ведёт полный цикл: от исследования рынка до монетизации.

## 2. ИНФРАСТРУКТУРА

```
Ubuntu 24 Server
  └── Docker Compose (все сервисы в контейнерах)
        ├── Frontend (Next.js — веб-панель управления)
        ├── Backend API (FastAPI)
        ├── Agent Runtime (движок агентов + Celery Workers)
        ├── Task Engine (доска задач)
        ├── PostgreSQL (основная БД)
        ├── Redis (очереди, кеш, pub/sub, WebSocket broker)
        ├── MinIO (файловое хранилище артефактов агентов)
        ├── Nginx (reverse proxy + robots.txt + rate limiting)
        └── WireGuard VPN

Cloudflared Tunnel → ai-devstudio.mak-o.ru
VK API → личное сообщение владельцу в группе
```

### Безопасность доступа к веб-панели

- Аутентификация: логин + пароль (хэш bcrypt)
- Хранение: `LOGIN` и `PASSWORD_HASH` в `.env` (не в БД)
- JWT-сессии с коротким TTL + refresh token в httpOnly cookie
- Nginx: закрытые заголовки, `X-Robots-Tag: noindex, nofollow`
- `robots.txt`: `Disallow: /` для всех crawlers
- Rate limiting на логин-эндпоинте (защита от brute force)
- HTTPS принудительно через Cloudflared
- Один аккаунт — один владелец, регистрация отсутствует

## 3. AI-ПРОВАЙДЕРЫ И МОДЕЛИ

### 3.1 Поддерживаемые провайдеры

| Провайдер | Тип доступа | Особенности |
|-----------|-------------|-------------|
| **Codex** | OAuth (multiple accounts) | Можно выжимать по максимуму |
| **DeepSeek** | API Key | Reasoning-heavy задачи |
| **Google AI Studio** | API Key | Gemini-модели |

### 3.2 Мультиаккаунт Codex OAuth

- Хранение нескольких OAuth-аккаунтов Codex в системе
- Ручное переключение активного аккаунта в настройках
- **Авто-переключение:** при достижении лимита — автоматический переход на следующий аккаунт в очереди
- Визуальный индикатор лимитов по каждому аккаунту (использовано / осталось / сброс через N)
- Порядок переключения настраивается вручную

### 3.3 Назначение провайдера и модели на агента

- Для **каждого агента** индивидуально выбирается: провайдер + конкретная модель
- Смена провайдера/модели — в настройках команды, без перезапуска системы
- Пример конфига агентов:
```
Директор:       DeepSeek / deepseek-reasoner
Backend Dev:    Codex OAuth / account-1
Frontend Dev:   Codex OAuth / account-2
Аналитик:       Google AI Studio / gemini-2.0-flash
```

### 3.4 Лимиты и метрики использования

Настройки лимитов — в разделе **Настройки → Провайдеры**, индивидуально под каждый:

```

│  Дневной лимит токенов: [не ограничен ▾]              │

| 4 | **Backend-разработчик** | Backend Dev | Архитектура, API, серверная логика, БД, интеграции |
| 5 | **Frontend-разработчик** | Frontend Dev | UI-реализация, веб-интерфейсы продуктов, SPA/SSR |

| 9 | **Маркетолог** | Marketer | Стратегия продвижения, воронки, платная реклама, аналитика конверсий |
| 10 | **Копирайтер** | Copywriter | Тексты продукта, лендинги, рекламные материалы, tone of voice |

│  Tool Use:                               │

### 4.3 Skills (навыки агентов)

- Каждый агент имеет набор Skills — специализированных инструментов/промптов для конкретных операций
- Skills хранятся в базе, версионируются
- Агент **создаёт новый Skill**, если обнаружил повторяющийся паттерн
- Директор может **распространить Skill** на других агентов
- Управление: Настройки → Команда → [Агент] → Skills

## 5. СИСТЕМА АВТОНОМНОСТИ И СОГЛАСОВАНИЯ

### 5.1 Режимы автономности (настраивается per-project)

```
РЕЖИМ 1 — «Полная свобода»
  Агенты работают без согласований с владельцем.
  Владелец получает только финальные результаты.
  Применение: простые, типовые, низкорисковые проекты.

РЕЖИМ 2 — «Согласование этапов» (рекомендуемый)
  Согласуются переходы между крупными этапами.
  Внутри этапа — полная автономия агентов.
  Применение: большинство проектов.

РЕЖИМ 3 — «Жёсткий контроль»
  Каждое значимое решение выносится на согласование.
  Финансовые действия — только с подтверждения владельца.
  Применение: сложные, высокорисковые, новые направления.
```

### 5.2 Гибкая настройка триггеров согласования

В настройках каждого проекта — чеклист того, что **обязательно требует одобрения**:

```
☑ Выбор направления / продукта
☑ Финансовые расходы свыше: [___] руб
☑ Публикации в соцсетях
☑ Запуск рекламных кампаний
☑ Деплой в production
☐ Создание задач агентами
☐ Написание кода
☐ Создание текстового контента
☐ SEO-правки на сайте
```

### 5.3 Принцип «только согласованные проекты»

- Ни один проект не стартует без утверждения владельцем
- Агенты предлагают направления → владелец выбирает → агенты исполняют
- После утверждения — работают автономно в рамках настроенного режима
- Инициативы за пределами согласованного скоупа — только через запрос

## 7. ФАЙЛОВОЕ ХРАНИЛИЩЕ (MinIO)

- **MinIO** — S3-совместимое локальное объектное хранилище в Docker
- Используется для: артефактов агентов, загруженных файлов, медиа-контента, бэкапов БД, скриншотов QA, макетов дизайна
- Доступ: только из внутренней Docker-сети (не публичен снаружи)
- Веб-консоль MinIO: отдельный внутренний порт (не через Cloudflared)
- Структура бакетов: `projects/`, `agents/`, `products/`, `backups/`

  "status": "in_progress",
  "priority": "high",
  "parent_task": "TASK-0038",
  "subtasks": ["TASK-0043", "TASK-0044"],
  "dependencies": ["TASK-0041"],
  "requires_approval": false,
  "live_plan": {
    "steps": [
      { "step": "Изучить макеты от UX/UI", "status": "done" },
      { "step": "Настроить структуру компонентов", "status": "in_progress" },
      { "step": "Реализовать секции", "status": "pending" },
      { "step": "Адаптив + кросс-браузер", "status": "pending" },

  },
  "comments": [],
  "attachments": [],
  "tags": ["frontend", "landing"]
}
```

### 9.2 Доска задач (Kanban+)

```
BACKLOG → TODO → IN PROGRESS → REVIEW → AWAITING APPROVAL → TESTING → DONE → ARCHIVED
```

- Карточки **автоматически** перемещаются агентами по ходу работы
- `AWAITING APPROVAL` — статус для задач, требующих решения владельца (подсветка на дашборде)
- Блокировки отображаются явно (задача ждёт другой)
- Фильтрация: по агенту / проекту / приоритету / статусу / тегу

### 9.3 Коммуникация агентов

- Вся коммуникация — **в комментариях к задаче** (полная трассируемая история)
- Агент → Директор: уточнение, отчёт о выполнении, блокер
- Директор → Агент: ответ, коррекция, постановка подзадачи
- Директор → Владелец: только то, что не может решить сам
- Владелец → Любой: через карточку задачи или комментарии к ней

### 9.4 Живой план задачи

- Агент **обязан** составить живой план при взятии задачи в работу (до начала действий)
- Формат: пронумерованный чеклист шагов с текущим статусом каждого
- Обновляется в реальном времени по ходу работы
- Если шаг выполнен иначе, чем планировалось — агент фиксирует причину в плане
- Директор видит планы всех активных задач в разделе Мониторинг

### 10.3 Мониторинг

Полная картина. Структурированные вкладки:

**📋 Задачи** — все задачи всех проектов, фильтры, временная шкала, зависшие по SLA

**💰 Финансы** — выручка real-time по продуктам, расходы, прибыль, тренд

**📜 Логи** — полный audit trail действий агентов (фильтр: агент / проект / тип / время)

## 11. СИСТЕМА УВЕДОМЛЕНИЙ

### Каналы

- **VK API:** личное сообщение владельцу в чате группы (приоритетный канал)
- **Веб-панель:** колокольчик + центр уведомлений

### Типы и приоритеты

| Тип | Приоритет | Пример |
|-----|-----------|--------|
| Требует решения | 🔴 Критический | «Директор: выберите направление по проекту X» |
| Блокер | 🟡 Высокий | «TASK-041 заблокирована: нет доступа к API» |
| Завершение этапа | 🟢 Средний | «Проект Y: этап Разработка завершён» |
| Финансовое событие | 💰 | «Первая оплата: Сонник-бот, 199 ₽» |
| Лимит провайдера | 🔄 | «Codex account-1: лимит исчерпан → переход на account-2» |
| Системная ошибка | ⚠️ | «Сервис agent-runtime недоступен 5 мин» |
| Ежедневный дайджест | 📊 | Сводка дня (время настраивается) |

### Гибкость

- Каждый тип: включить / отключить
- Выбор канала для каждого типа: VK / веб / оба
- Тихий режим: настраиваемое расписание (например, 23:00–8:00)

## 15. ПРИНЦИПЫ РАБОТЫ СИСТЕМЫ

1. **Автономность по умолчанию** — агенты работают самостоятельно в рамках согласованного скоупа
2. **Только согласованные проекты** — ни один продукт не запускается без утверждения владельцем
3. **Гибкий контроль** — каждый проект настраивается: от полной свободы до жёсткого согласования
4. **Прозрачность абсолютная** — каждое действие агента логируется и видно в панели
5. **Всё оцифровано** — нет решений «в голове»; план, статус, результат — только в системе
6. **Синхронизация команды** — агенты работают в едином контексте, общаются через задачи
7. **Маркетинг пронизывает всё** — каждый агент оценивает влияние своих решений на продукт
8. **Эскалация — норма** — лучше уточнить, чем потратить ресурсы на неверное решение
9. **Безопасность** — закрытый доступ, JWT, .env-конфигурация, запрет индексирования
